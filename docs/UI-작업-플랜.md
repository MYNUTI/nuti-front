# UI 작업 플랜

> 상태: **초안** (2026-11-02). 이 문서는 범위·순서·결정만 기록한다. 화면 하나가 끝날 때마다 확인받고 다음 화면으로 넘어간다.

## 목적

피그마 「Design v3 · 새로 (2026-10-22)」 페이지의 화면을 코드로 옮긴다.

- 만드는 것: 디자인 토큰, 공통 부품, 화면(라우트)과 화면 안 상태(로딩·에러·빈 상태·분기)
- 건드리지 않는 것: `src/lib/` 안쪽 전부. API 작업 브랜치(`feat/api`)와 겹친다. 이미 있는 `lib/scan`·`lib/utils`·`lib/grade`는 import만 한다
- 피그마에 없거나 메모에 「안 정함」으로 남은 부분은 추측해서 채우지 않는다. 「남은 질문」으로 남긴다

## 현재 코드 (2026-11-02 확인)

- `globals.css` 토큰은 예전 피그마 Primitive·Semantic 값이다(딥그린 주색, 파랑~빨강 등급색). v3 CHIPS 토큰(라임 `#84F01C` 주색, 등급 A `#40CF52` ~ E `#F73756`)과 이름·값이 모두 다르다
- 글꼴은 Paperlogy(로컬 woff2 2종). 피그마는 Noto Sans KR이고, 메모상 원래 의도는 Pretendard다(피그마 도구에 없어 대체)
- 공통 부품: `components/common/`(grade, tab-bar, cta-button, layer, card-tutorial, choice-card), `components/ui/`(shadcn button, checkbox, radio-group)
- 스캔: `components/scan/`가 `lib/scan` 상태 기계·lookup에 붙어 있다. UI 작업은 겉모양만 바꾸고 이 연결은 유지한다
- 라우트는 임시본이다(`home`, `scan`, `history`, `settings`, `product/[id]`, `onboarding/*` 9개). v3 화면 구성과 맞지 않는다

## 작업 방식

화면 하나(위 표의 한 줄)마다 아래 순서로 하고, 끝나면 확인받는다.

1. 기본 프레임과 상태 프레임 전부, 메모, 상태표 줄을 읽는다
2. 화면에 필요한 데이터를 **화면 props 타입**으로 정한다. API 타입(`lib/<도메인>/types.ts`)은 API 브랜치 몫이라 여기서 만들지 않는다
3. 공통 부품을 우선 쓰고, 없는 부품은 00단계 부품에 추가할지 화면 전용으로 둘지 정한다
4. 상태 프레임을 모두 재현한다. 서버 응답이 필요한 상태는 임시 데이터로 고정해서 확인한다(아래 「데이터」)
5. 메모의 「누르면」 이동을 연결한다. 아직 없는 화면으로 가는 링크는 경로만 걸어 둔다
6. `pnpm typecheck`, `pnpm lint`, `pnpm test` 통과 → 개발 서버에서 피그마 스크린샷과 비교 → 확인 요청

### 데이터

API 연결은 API 브랜치 08·09단계 이후에 붙인다. 그 전까지 화면은 props로만 데이터를 받는다.

- 임시 데이터는 화면 폴더 옆(`src/app/<경로>/_fixtures.ts`)에 둔다. `src/lib/`에 두지 않는다
- 나중에 연결할 때는 fixture import를 쿼리 훅 + mapper로 바꾸는 것만 남도록, 화면 props는 서버 필드 이름이 아니라 화면이 쓰는 모양으로 정한다
- 담기·즐겨찾기·지우기처럼 서버 변경이 필요한 동작은 지금은 화면 안 상태로만 처리한다

### 00단계 상세

1. **토큰** — `globals.css`의 예전 토큰을 CHIPS v3 값으로 바꾼다. 색(brand·accent·text·bg·line·icon·tab), 등급 색 ④-3(A~E, 배지 글자는 모두 검정), 글자 스타일 11개, 간격(4·8·12·16·20·24·32·40), 모서리(sm 8·md 12·lg 16·sheet 20·pill). shadcn 별칭도 새 토큰을 가리키게 한다
2. **글꼴** — 「남은 질문」 1번 답에 따른다
3. **아이콘** — 피그마 v2/Icon 24px 선 아이콘 약 40개. lucide로 대응되는 것과 SVG로 옮길 것을 나눈다
4. **부품** — 피그마 「부품」 판 기준. 기존 `components/common`은 고치거나 바꾼다
   - 버튼 · BottomCTA(single, double, icon+single, filter)
   - TopBar(back·close, light·dark) · SearchField · TabBar(홈·랭킹·스캔·기록·내 정보, 가운데 스캔 강조)
   - GradeBadge(sm·md) · GradeTag(A~E 문구) · StatusTag(분석 전·확인 중)
   - Chip(filter·removable·dropdown) · SelectCard · Checkbox · TextField
   - ProductRow · ProductItem(격자) · ListRow(none·toggle·chevron) · ReasonRow(good·bad) · SectionHeader
   - Thumb · CategoryTile · CameraFrame(barcode·label)
   - 바텀시트·확인 대화상자(5-5 계정 삭제, 5-7c 등에서 씀)
5. **공통 상태** — 불러오는 중·불러오지 못함·0건 패턴
6. **라우트 표** — 아래 초안을 확정한다

## 다른 브랜치와 겹치는 곳

`feat/api`는 아직 `main`과 같다(2026-11-02). API 플랜에서 아래 파일을 고칠 예정이라 UI 작업과 겹친다.

- `src/app/home/page.tsx`, `src/app/product/[id]/page.tsx` — API 06단계에서 목 카탈로그 import 경로를 바꾸고, 상세 페이지에 서버 조회를 넣는다
- `src/components/scan/scan-stage.tsx` — API 06단계에서 쿼리 키를 옮긴다
- `src/app/providers.tsx` — API 07단계. UI 작업은 건드리지 않는다

화면 파일은 UI 쪽에서 새로 쓰게 되므로, 겹치는 파일은 먼저 머지되는 쪽에 맞춰 다른 쪽이 리베이스한다. 리베이스 시점은 확인받는다.

## 남은 질문

1. **글꼴** — Pretendard(메모상 원래 의도) / Noto Sans KR(피그마 그대로) / Paperlogy(지금 코드) 중 무엇을 쓰나
2. **데이터** — 「데이터」의 화면 옆 fixture 방식으로 가도 되나. 아니면 API 훅이 나온 도메인부터 화면을 붙이나
3. **라우트** — 「라우트 초안」대로 가도 되나. 기존 `/onboarding/*` 9개 라우트는 13단계에서 지워도 되나
4. **0-1 스플래시** — PWA 스플래시(`src/lib/pwa.ts`·`public/pwa/splash/`)와 앱 안 스플래시 화면이 둘 다 필요한가. 토큰 교체 후 `SPLASH_COLOR`(지금 `#2f6758`) 변경과 `pnpm pwa:assets` 재생성은 `src/lib/` 금지의 예외로 둘지
5. 메모의 「안 정함」 항목 — 화면 작업 때 해당 화면 것을 모아 묻는다
