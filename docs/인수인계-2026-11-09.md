## 꼭 알아야 할 주의점

1. **개발 서버가 없다. 개발 중에도 배포 서버(운영 데이터)를 부른다.** 팀이 허용한 부수 효과지만 최소화한다
   - 상품 조회만 해도 조회수가 오르고(인기·추천 정렬에 반영), 없는 바코드는 분석 대기 목록에 등록된다
   - 변경 API·로그인도 운영 데이터에 남는다. 실험 삼아 반복 호출하지 않는다
2. **`src/lib/`은 API 작업, `src/app`·`src/components`는 UI 작업 영역**이다. UI 작업 중 `src/lib/`은 import만 한다(예외: `lib/pwa.ts`의 `SPLASH_COLOR`, `lib/utils.ts`의 `cn`). API 작업(06단계 스캔·상세 연결, `/grades/guide` 데이터 레이어)을 같이 할 때는 해당 `src/lib/` 파일과 테스트를 고친다(목 `lookupProduct`는 `lib/scan/lookup.ts`·`lookup.test.ts`, `ScanResult`는 `lib/scan/types.ts`)
3. 현재 `src/app` 라우트 중 v3 디자인으로 다시 만든 것은 `/`, `/intro`, `/intro/2`, `/intro/goal`, `/home`, `/scan`의 0-3·0-3x·3-1(기본과 상태 6개, 아래 「UI 현황」), `/product/[id]` 3-2 기본 화면뿐이다. 3-1의 조회 결과 시트·카메라 점유 띠와 나머지(`history`, `settings`, `onboarding/*`)는 **임시본이라 기준으로 삼지 않는다**. `history`·`settings`는 해당 단계에서 같은 경로로 다시 만들고, 대체된 `onboarding/*`는 13단계에서 지운다
4. 스캔 조회(`src/lib/scan/lookup.ts`의 `lookupProduct`)는 아직 목 카탈로그(`src/lib/mock-catalog.ts`)를 쓴다. 상품 상세(`/product/[id]`)는 `src/app/product/[id]/_fixtures.ts`, 홈은 `src/app/home/_fixtures.ts`를 쓴다(`findProductById`는 이제 테스트에서만 쓴다). 홈의 「최근 본 제품」은 맞는 1차 API가 없어 연결하지 않는다
5. 피그마·명세에 없거나 「안 정함」인 부분은 추측해서 채우지 않는다. 플랜 문서의 「남은 질문」에 적고 넘어간다

- `main`에 PR로 머지한다. 지금까지는 `feat/api`, `feat/ui`에서 머지했다(PR #2, #3)

### 남은 것

1. **06단계 화면 연결 — 스캔·상세** (UI 03·04단계와 같이 하는 게 맞다)
   - `src/components/scan/scan-stage.tsx`를 `lookupProduct`(목) → `useProductByBarcode`로 바꾸고 등급 없음(`INSUFFICIENT`)·미등록(404)·체크섬 오류 분기를 넣는다. 3-1 숫자로 입력 시트(`scan-manual-sheet.tsx`)는 디자인 메모대로 체크섬이 틀리면 조회하지 않고 오류만 보인다. `lib/scan/gtin.ts`의 `checkGtinInput` 설명(「empty만 제출을 막는다」)과 다르니 이때 맞춘다. 앞자리가 0이 아닌 14자리 직접 입력(400)을 입력 단계에서 막을지 정한다. 목 `lookupProduct`·`ScanResult`는 지운다
   - `src/app/product/[id]/page.tsx`를 `getProductDetail` + `notFound()` + `HydrationBoundary`로 바꾼다. **서버 prefetch용 QueryClient는 `retry`를 끈다**(안 끄면 조회수가 두 번 오를 수 있다)
   - 실제 서버로 확인: `cache()` 중복 제거, 스캔 → 상세 이동, proxy 갱신 뒤 개인 기준 등급 렌더
2. **나머지 화면 연결** — 각 화면의 `_fixtures.ts` import를 쿼리 훅 + mapper로 바꾼다. 맞는 1차 API가 없는 값(홈 「최근 본 제품」, 2차 범위인 등급 순위 등)은 fixture로 둔다. 화면 연결 때 챙길 것(버튼 `isPending` 잠금, 동의 게이트 감싸는 법, 검색 디바운스·30자 제한 등)은 API 플랜 「화면 연결 때 챙길 것」에 정리돼 있다. **연결 전에 꼭 읽을 것**
3. **11단계 OAuth 콜백 화면** — 아래 「막힌 질문」 1~3번 답이 와야 시작할 수 있다
4. 토스트·세션 만료 알림 UI — 데이터 쪽은 `setMutationErrorListener`, `onSessionExpired`까지 있고 화면이 등록만 하면 된다. 알림 띠 부품은 `components/common/toast.tsx`(`Toast`)에 있다
5. **`GET /grades/guide` 데이터 레이어** — 5-4 「등급은 어떻게 매기나」(UI 04단계)가 쓴다. 아직 API 함수·훅이 없어 `src/lib/product/`에 다른 도메인과 같은 구조로 만든다. API 플랜 매핑표는 식별을 「없음」으로 적었지만 백엔드(`GradeController`)는 식별을 받아 `goal`을 생략하면 내 목표(없으면 GENERAL)로 답한다. 식별을 붙일지, `goal`을 항상 보낼지 만들 때 정한다

    - 아쉬운 점이 없으면 「아쉬운 점」 머리 아래 「이 목표에서 아쉬운 점이 없어요」(메모). 미리 보는 중이면 그 목표의 이유 기준이다
    - 「더 맞는 제품이 없을 때, 담았을 때」는 기존 담기 동작(비교함 바)과 같아 따로 만들 것이 없다
    - **API 06단계 주의:** 등급(A–E)과 점수 구간은 스캔 시트와 같게 A→1 … E→5로 본다(`scan-stage.tsx`의 `GRADE_BAND`). 더 맞는 제품 목록이 비면 이 줄이 뜬다
  - 3-2 사진이 없을 때(`src/app/product/[id]/product-photo.tsx`의 `ProductPhoto`): 사진이 없거나 주소가 깨지면(`onError`) 큰 칸에 「사진 없음」 그림(`public/common/no-photo.png`, 디자인 그림을 512px로 줄임) + 「제품 사진이 아직 없어요」. 대체 글은 「제품 사진 없음」이고 문구는 화면 읽기에서 뺀다. 비교함 바의 작은 사진도 같은 그림만 보인다(메모 「작은 칸은 그림만」)
    - 메모는 목록·작은 칸(`Thumb`, 스캔 결과 시트, 제품 줄)에도 같은 그림을 쓰라고 한다. 이 화면 밖이라 아직 바꾸지 않았다. 지금 `Thumb`는 사진이 없으면 회색 칸만 보인다
  - 3-2 생산 중단(`page.tsx`, 화면용 모양의 `production`): 브랜드 줄 끝에 받은 상태 글자(「단종」·「생산 중단 · 재고 판매 중」), 목표 칩 아래 회색 안내 상자 「제조사가 생산을 멈춘 제품이에요. 비슷한 제품을 찾아볼 수 있어요.」, 더 맞는 제품 칸은 점수 바로 아래로 올린다(메모 「생산 중단 화면만 위쪽」). 단종(`inStock: false`)이면 쿠팡 버튼·고지를 빼 「비교함 담기」 하나만 남는다. 재고 판매 중이면 쿠팡 버튼이 있다
    - 더 맞는 제품이 0개면 안내 상자의 둘째 문장(「비슷한 제품을 찾아볼 수 있어요.」)을 뺀다. 아래 「…아직 찾지 못했어요」와 어긋나서다. 디자인에 없는 조합이라 디자이너 확인(UI 플랜 「남은 질문」 12). 미리 보는 중에는 「내 목표로」에서 다시 볼 수 있어 남긴다
    - **API 06단계 주의:** 제품 상태 응답(`ProductStatus`)은 `ANALYZED`·`INSUFFICIENT`뿐이라 생산 중단·단종을 알 수 없다(아래 백엔드 10). 값이 생기면 mapper에서 `production`을 채운다
  - 3-2 내 몸에 맞춤(`page.tsx`, 화면용 모양의 `bodyFitKcal`): 내 몸에 맞추기를 켰고 지금 보이는 등급이 다이어트 기준이면 맞춘 값이다. 다이어트 목표면 목표 칩이 「다이어트 · 내 몸에 맞추기」, 펼친 영양성분 아래 설명이 「등급은 내 몸에 맞춘 칼로리(하루 약 2,680kcal)로 계산했어요. 표의 %는 식품 표시 기준(2,000kcal)이에요.」. 1일 기준치 %는 그대로다
    - 근육 증가 목표면 칩은 「근육 증가 · 내 목표」 그대로이고, 「체중 감량으로 보기」 미리 보기에서만 설명이 내 몸에 맞춘 문장으로 바뀐다(메모). 미리 보기 칩(「다이어트 · 미리 보기」, 「내 목표(다이어트)로는 n점」) 글자는 디자인에 없어 그대로 둔다(UI 플랜 「남은 질문」 13)
    - 메모 「같은 기준 글자를 목록 머리(기록, 저장, 비교, 순위)에도」는 그 화면들(05·07·09단계)에서 붙인다
    - **API 06단계 주의:** 내 몸에 맞추기 여부·하루 칼로리를 주는 API가 아직 없고(`/me/*`·온보딩 응답에 신체 정보 없음), 등급 이유 조회(`fetchGradeReason`)도 `goal`만 받는다(아래 백엔드 11). 서버 등급이 맞춘 칼로리로 계산돼 올 때만 `bodyFitKcal`을 채운다. 그렇지 않은데 채우면 「내 몸에 맞춘 칼로리로 계산했어요」가 사실과 다른 문장이 된다

`components/common/` 중 `cta-button`, `layer`, `card-tutorial`, `choice-card`와 `components/ui/`(shadcn)는 임시 화면용이다. 새 화면에서 쓰지 않는다.

### 화면 작업 순서 (화면 하나마다)

1. 기본 프레임 + 상태 프레임 전부 + 메모 + ⑩ 상태표 줄을 읽는다
2. 화면 props 타입을 **화면이 쓰는 모양으로** 정한다(서버 필드 이름 아님). API 타입은 만들지 않는다
3. 공통 부품을 먼저 쓰고, 없으면 공통 부품으로 추가할지 화면 전용으로 둘지 정한다
4. 상태 프레임을 모두 재현한다. 서버가 필요한 값은 `src/app/<경로>/_fixtures.ts`에 둔다(`src/lib/`에 두지 않는다)
5. 메모의 「누르면」 이동을 연결한다. 없는 화면은 경로만 건다
6. 검증 명령 통과 → 피그마 스크린샷과 비교

## 막힌 질문 (답 받으면 플랜 문서 「진행 가정」·「남은 질문」 갱신)

백엔드:

1. OAuth 콜백이 리다이렉트하는 `frontendUrl` 경로
2. 소셜 로그인 시작 URL에 쓸 소셜별 `client_id`·`redirect_uri`
3. OAuth `state`를 백엔드가 넘겨줄지(없으면 로그인 CSRF 방어 불가, 네이버는 필수)

5. 개인정보·건강정보 동의 항목 코드 확정값
6. 동의 없이 온보딩을 끝낸 사용자의 완료 상태 동기화 방식
7. 응답 필드의 필수·null 여부, 배포 서버 값이 백엔드 소스(`c164ec0`)와 같은지

9. 3-2 「정보가 틀렸어요」 제보를 보낼 API — 제품 ID·고른 항목(여러 개)·자세한 내용·영양성분표 사진을 받는 곳이 있는지(`/support/inquiries`는 내용·분류·이메일만), 같은 제보 중복 응답, 사진 보관 기간(CTRB_003)
